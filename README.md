# Floodlight

**Every moment, under the floodlights.**

[![ci](https://github.com/JinYi123456/floodlight/actions/workflows/ci.yml/badge.svg)](https://github.com/JinYi123456/floodlight/actions/workflows/ci.yml)

A live football intelligence pipeline. Synthetic match events go in — an
explainable, verified, broadcast-ready production comes out. Floodlight is
three products that share one spine:

- **Match intelligence** — a deterministic engine that reads the event stream
  the way an analyst would: possession value, xT, control-vs-chaos, rhythm,
  momentum and fourteen kinds of moment, each with the evidence it cites.
- **An automated production crew** — Director, Analyst, Commentator, Verifier
  and Personalizer agents that turn moments into air-ready stories. Nothing
  reaches air unless a deterministic fact gate can verify every number and
  every name in it.
- **Auto-eventing from pixels** — a vision pipeline that watches the rendered
  feed, re-derives passes, shots and speeds from raw colour, and honestly
  scores itself against the events the simulation actually produced.

**Live demo:** https://jinyi123456.github.io/floodlight/ — pick a storyline,
take it to air, and watch the control room play a full match in real time
(3D broadcast monitor, insight desk, rundown, cue sheet).

All clubs, players and matches are fictional. Every match is generated by a
seed and is fully reproducible.

## The pipeline

| Stage | What happens | Where |
| --- | --- | --- |
| **Ingest** | A seeded simulator plays a full 90 minutes as typed events (passes with difficulty & outcomes, carries, duels, shots with xG, set pieces, cards, substitutions, VAR) plus a 10 Hz positional feed. | `packages/simulator` |
| **Interpret** | A deterministic engine reduces the stream to live states — time-weighted possession, expected threat, control-vs-chaos, tactical pressure, rhythm, momentum — and lifts out insight candidates with evidence ids. | `packages/engine` |
| **Explain** | The production crew directs, drafts, verifies and rewrites. The verifier rejects unverifiable numbers, unknown names and claims about records, seasons or history; templates are the deterministic floor. Verified copy can come from a recorded studio voice. | `packages/agents` |
| **Render** | Approved stories compile into a versioned cue sheet — lower thirds, stat bumpers, momentum ribbon, telestration, player tags, goal flashes — with priorities, slot exclusivity and expiry. | `packages/cuesheet` |
| **Personalize** | The same verified story reaches an analyst, a casual fan, a club supporter or a player-focus viewer — in English, Spanish or French, from recorded or template variants. | `packages/agents` |

The web app runs the whole pipeline **in a worker**: matches precompute, then
play back against a theatre clock — a 3D broadcast monitor with three camera
presets, a retraction-aware rundown (a VAR-overturned goal pulls its story
off air), an insight desk with the evidence trail, and the cue sheet driving
the on-screen graphics. A **catch-up** viewer mode is spoiler-safe: the
rundown and the scrubber keep everything past the viewer's high-water mark
hidden until they actually get there — watch it late, see it fresh.

## Data & assets

The simulation is football-realistic and checked as such: a 20-match test
fixture asserts aggregate texture on every run (~3.4 goals, ~26 shots, ~82%
pass accuracy, ~17 fouls, ~8 corners per match), seeded so the same seed
yields the byte-identical event stream on any machine. Scripted storylines
(`comeback`, `siege`, `derby`) choreograph dramatic matches — including a
VAR overturn — so the pipeline always has a real story to discover, explain
and retract.

`npm run export:dataset` writes a full, portable record of every scenario to
`data/`: the raw event stream and the insight feed (JSONL), stories with
provenance (JSONL + CSV), per-player stats, the compiled cue sheet, and a
generated `DATA_CARD.md` covering schemas, provenance and regeneration. The
committed exports under `data/` are the byte-identical output of scenario
+ seed — no timestamps, no machine-dependent values.

```
data/comeback-2026/   3–2 · 2118 events · 31 stories · 53 cues
data/siege-2026/      1–0 · 2194 events · 29 stories · 39 cues
data/derby-2026/      4–3 · 2144 events · 37 stories · 61 cues (VAR overturn)
data/freeplay-2026/   1–0 · 2205 events · 17 stories · 25 cues
```

## Auto-eventing (vision)

`packages/vision` renders the match to a sensor image — mow stripes,
markings, kit-coloured discs, a bright ball — and then forgets everything it
knows. A blob detector learns both kits' palettes, finds the ball and the
players; a velocity-predicted tracker follows them; a state machine derives
passes, shots, possession and speeds with no access to ground truth. The
report card scores the result against the simulator's own stream (the
scored pass runs a 320×208 sensor; the live vision lab renders at 640×416):

| metric | measured on the marquee window |
| --- | --- |
| pass precision / recall / F1 | 100% / 50% / 67% |
| shots | 1 of 1 detected |
| ball speed error | 3.6 km/h |
| player speed error | 2.1 km/h |
| possession agreement | 88% |
| frames processed | 901 (90 s clip at 10 Hz) |

The vision lab in the web app plays the same feed live, draws its detections
over the pixels and shows the accuracy report next to it. Misses are shown
as misses — the report is scored, not staged.

## Studio voice

`npm run record:voice` runs the real crew against an OpenAI-compatible
gateway (Featherless by default; `FEATHERLESS_API_KEY` in `.env.local`),
verifies every draft, and freezes the output into
`apps/web/public/recordings/*.json`. The deployed app plays that studio
voice for the story scenarios — **no key ever reaches the browser** — and
falls back to the deterministic template floor for anything unrecorded or
for a different seed.

## API

`npm run api` serves the same pipeline over HTTP (zero runtime deps):

| endpoint | what it returns |
| --- | --- |
| `GET /scenarios` | the four storylines with their clubs |
| `GET /matches/prepare?scenario=&seed=` | the full machine-readable run |
| `GET /matches/stream?scenario=&seed=` | **SSE**: stage → moment → ready → done, live |
| `GET /matches/vision?scenario=&seed=` | the auto-eventing accuracy report |
| `GET /matches/events.jsonl` · `/moments.csv` · `/data-card` | dataset formats |
| `POST /mcp` | the studio as **MCP** tools over Streamable HTTP |

```bash
curl -N "http://localhost:8787/matches/stream?scenario=derby&seed=2026"
```

A `Dockerfile` ships it as a single container (`docker build -t floodlight-api .`
from the repo root).

**It is also live on Azure** (Container Apps, consumption plan, scale-to-zero):

https://floodlight-api.lemonsmoke-f1226dd0.southeastasia.azurecontainerapps.io/

```bash
curl -N "https://floodlight-api.lemonsmoke-f1226dd0.southeastasia.azurecontainerapps.io/matches/stream?scenario=comeback&seed=2026"
```

## MCP — the studio as tools

The whole studio is exposed as a typed **Model Context Protocol** tool
surface — nine tools: `list_scenarios`, `prepare_match`, `match_state`,
`state_at`, `query_events`, `query_moments`, `player_stats`, `get_cue_sheet`
and `run_vision_pass`. Three real consumers ride on it (`services/mcp`):

- **External agent hosts** attach over stdio: `npm run mcp` speaks the full
  handshake; point any MCP client at `floodlight-mcp`.
- **Remote hosts** attach over Streamable HTTP at `POST /mcp` on the API
  service — stateless, so the container scales to zero.
- **The crew itself** verifies over MCP: the production crew's fact-checking
  (snapshot, score at time t, window features) runs as real tool calls over
  an in-process transport — the browser worker links it to the live engine,
  and a parity test proves the routed path is byte-identical to reading the
  engine directly.

A live-match tool set (`match_snapshot`, `match_score_at`,
`match_window_features`) backs the crew's path; a framework-agnostic data
service (`packages/dataservice`) backs every tool, so the verification the
audience sees is the verification the tools serve.

## Quickstart

```bash
npm install
npm test            # deterministic suite: simulator, engine, agents, cues,
                    # vision, dataset, api, mcp
npm run dev         # the web app (Vite dev server)
npm run api         # the HTTP/SSE service (and POST /mcp on the same port)
npm run mcp         # the studio as an MCP server over stdio
npm run export:dataset    # regenerate data/
npm run record:voice      # refresh the studio-voice recordings
```

```ts
import { simulateMatch, SCENARIOS, trackingWindow } from '@floodlight/simulator';
import { MatchEngine } from '@floodlight/engine';
import { ProductionCrew } from '@floodlight/agents';
import { compileCues } from '@floodlight/cuesheet';

const result = simulateMatch(2026, SCENARIOS.find((s) => s.id === 'comeback'));
const engine = new MatchEngine(result.meta, result.lineups);
const candidates = result.events.flatMap((e) => engine.ingestEvent(e));
const frames = trackingWindow(result, 0, result.timing.fullTimeT, { hz: 2 });
for (const frame of frames) candidates.push(...engine.ingestFrame(frame));

const crew = new ProductionCrew();
const moments = [];
for (const c of candidates.sort((a, b) => a.t - b.t)) {
  const m = await crew.processCandidate(c, engine);
  if (m) moments.push(m);
}
const cues = compileCues(moments, result.meta, { events: new Map(result.events.map((e) => [e.id, e])) });
console.log(moments.map((m) => `${m.candidate.minuteLabel} ${m.headline}`).join('\n'));
```

## Repository layout

```
packages/core        domain model, seeded RNG, pitch maths
packages/simulator   seeded match engine, storylines, tracking, calibration
packages/engine      live football intelligence and insight candidates
packages/agents      director/analyst/commentator/verifier/personalizer crew
packages/cuesheet    timed, machine-readable broadcast graphics compiler
packages/vision      auto-eventing: pixels → detections → derived events
packages/dataset     portable exports + generated data card
packages/dataservice one tool surface over the pipeline (studio + live)
services/api         HTTP/SSE service over the pipeline (+ Dockerfile)
services/mcp         the MCP servers: stdio host + in-memory crew transport
apps/web             control room: worker pipeline, 3D monitor, vision lab
tools                studio-voice recorder
data                 committed dataset records for the four scenarios
```

## Principles

- **Deterministic**: seeds everywhere; identical inputs, byte-identical
  outputs — asserted by tests, for events, stories, cues and rasters alike.
- **Evidence first**: every number in the product traces to an event or a
  frame-derived measurement. The verifier rejects whatever it cannot cite.
- **Honest perception**: the vision pipeline is scored against ground truth
  in public; its report card shows what it missed, not only what it found.
- **No real data**: a fictional league, fictional clubs, fictional players —
  football-realistic ranges, fully synthetic provenance.

## Deployment

CI typechecks, tests and builds on every push; `main` publishes the web
build to GitHub Pages automatically. The API ships as a container for any
free-tier Node host — the image is built and pushed to
`ghcr.io/jinyi123456/floodlight-api` by `.github/workflows/api-image.yml`
on the same pushes.

For **Azure Container Apps**, the whole runbook is
[`docs/deploy-azure.md`](./docs/deploy-azure.md): three `az` commands put the
API + MCP endpoint live on HTTPS with scale-to-zero inside the service's
free monthly grant. The reference deployment from this repo runs at
`floodlight-api.lemonsmoke-f1226dd0.southeastasia.azurecontainerapps.io`.
